\section{Introduction}

The internet has evolved beyond connecting people and computers to encompassing a vast network of physical objects and sensors, creating what is widely termed the Internet of Things (IoT). This proliferation of connected devices has driven an exponential increase in data volume and computational demand, while simultaneously heightening the need for low-latency processing and efficient analytics. When all data must traverse centralised cloud infrastructure, the result is network congestion, bandwidth inefficiency, and latency bottlenecks that undermine the real-time requirements of modern applications.

Edge computing addresses these challenges by relocating computation closer to the point of data generation, reducing long-distance data transfer and enabling faster, more localised processing \cite{kim2025exploring}. Rather than transmitting all raw data to a distant cloud data centre, edge nodes can perform initial processing, filter irrelevant information, and forward only meaningful results.

However, edge environments are inherently complex. They comprise numerous heterogeneous nodes---ranging from resource-constrained IoT sensors to modest edge servers---that experience dynamic and unpredictable workloads while operating under tight resource constraints \cite{rasouli2025false}. Managing such systems manually is impractical, which drives the need for automated container orchestration. Kubernetes has emerged as the de facto standard for this purpose, providing automated deployment, scaling, and fault handling for containerised applications across clusters of machines.

Yet effective orchestration depends critically on the \textit{scheduler}: the component responsible for assigning workloads (pods) to available nodes. The default Kubernetes scheduler is primarily designed for homogeneous data centres with stable, predictable resources \cite{liu2024dynamic}. It relies on declared resource requests rather than actual node utilisation and lacks awareness of runtime anomalies or future resource trends. This makes it poorly suited to the heterogeneous, volatile nature of edge environments, where nodes may experience sudden load spikes, connectivity issues, or resource exhaustion.

Several approaches have been proposed to improve scheduling in such contexts. Static schedulers that ignore runtime state entirely are ineffective in dynamic environments. Monitor-driven heuristics react to observed resource changes but are overly sensitive to noise and inherently backward-looking, struggling with transient workloads since they act only on past states \cite{pashaeehir2025kubedsm}. Machine learning--based anomaly detection can identify deviations from normal behaviour but typically produces binary classifications without directly informing scheduling decisions \cite{fritzsche2024lightweight}. Prediction models offer proactive resource forecasting but are rarely combined with anomaly awareness in a system lightweight enough for edge deployment.

This gap---the absence of a lightweight system that combines both anomaly detection and short-term prediction to inform scheduling---motivates the present work. This project aims to integrate a proven lightweight anomaly detection method with a resource prediction model within a custom Kubernetes scheduling component. By unifying detection and prediction in a scheduler-aware pipeline, the system seeks to avoid placing workloads on anomalous or soon-to-be-overloaded nodes, thereby improving scheduling latency, pod start-up time, and resource utilisation compared to the default Kubernetes scheduler.

\subsection{Project Objectives}

This project pursues three objectives:

\begin{enumerate}
    \item \textbf{Replicate baseline.} Simulate an edge cluster environment using Kubernetes on virtual machines and reproduce the baseline lightweight anomaly detection pipeline proposed by Fritzsche et al.~\cite{fritzsche2024lightweight}, covering data collection, preprocessing, and detection. Evaluate the default Kubernetes scheduler by analysing how detected anomalies correlate with scheduling outcomes such as node selection and performance impact.
    
    \item \textbf{Extend with lightweight prediction and custom scheduling.} Design and implement a lightweight machine learning model to predict short-term node resource utilisation. Integrate both the anomaly detector and the predictor into a custom scheduling component that scores nodes and makes placement decisions based on predicted load and anomaly risk.
    
    \item \textbf{Evaluate and compare.} Experimentally evaluate the integrated system against the default Kubernetes scheduler in a simulated edge cluster. Compare results on key performance metrics: scheduling latency, pod start-up time, placement safety, and resource contention.
\end{enumerate}


\section{Background Research}

\subsection{Edge Computing Fundamentals}

The emergence of cloud computing provided a scalable infrastructure for centralised data storage and processing, reducing the need for local physical hardware and enabling network growth. However, the introduction of IoT devices---sensors and embedded systems that generate and transmit data in real time---has resulted in massive volumes of telemetry traversing the network, much of it without immediate utility at the centralised cloud layer \cite{kim2025exploring}.

Edge computing addresses this inefficiency by moving computation as close as possible to the point of data collection. Rather than forwarding all telemetry to a remote data centre, edge nodes process data locally and transmit only aggregated or filtered results when necessary. This architecture reduces bandwidth consumption, lowers latency, and enables IoT devices to make locally informed decisions about what data merits long-distance transfer \cite{shen2025codesign}.

Edge networks are composed of heterogeneous devices, servers, and gateways, each referred to as a \textit{node}. Since many edge nodes are small, mobile, or battery-powered, the computational resources available for processing are inherently constrained. Furthermore, the geographically distributed nature of edge deployments introduces challenges related to network connectivity, synchronisation, and fault tolerance. As edge networks scale, the diversity of node capabilities increases, requiring orchestration systems capable of managing heterogeneous resources effectively \cite{rasouli2025false}.

These constraints---limited resources, heterogeneous hardware, dynamic workloads, and intermittent connectivity---make automated monitoring and anomaly detection essential for maintaining reliable operation. Without such mechanisms, edge deployments risk degraded performance, resource exhaustion, and cascading failures across dependent services.


\subsection{Kubernetes Architecture and Scheduling}

Kubernetes is a container orchestration platform that automates the deployment, scaling, and management of containerised applications across clusters of machines. Its architecture is divided into a \textit{control plane}, which manages overall cluster state, and one or more \textit{worker nodes}, which execute application workloads.

The control plane consists of several components. The \textit{API server} exposes the Kubernetes API and serves as the central interface for all cluster operations, scaling horizontally through multiple instances. The \textit{etcd} store provides a consistent, highly available backing store for all cluster configuration and state data. The \textit{scheduler} assigns unscheduled pods to suitable nodes through an algorithmic process. The \textit{controller manager} runs control loops that continuously reconcile the actual cluster state with the desired state defined by users.

Worker nodes run containerised applications and comprise three main components: the \textit{kubelet}, which ensures containers are running and healthy according to their pod specifications; \textit{kube-proxy}, which manages network rules enabling communication between pods and external clients; and the \textit{container runtime}, which handles the execution and lifecycle of individual containers.

The default scheduler uses a two-phase approach to assign pods to nodes. In the \textit{filtering} phase, nodes that do not satisfy a pod's requirements---such as resource requests, node selectors, or taints and tolerations---are eliminated. The remaining nodes are termed \textit{feasible nodes}; if none exist, the pod remains unscheduled until conditions change. In the \textit{scoring} phase, each feasible node receives a weighted score based on factors including resource availability, hardware and software constraints, affinity and anti-affinity specifications, data locality, and inter-workload interference. The highest-scoring node is selected and the assignment is communicated to the API server through a process called \textit{binding}.

Kubernetes provides mechanisms for scheduler customisation through \textit{scheduler profiles}, which can be selected at the command line or specified per pod. Each profile configures a series of \textit{extension points}---hooks in the scheduling pipeline where custom logic can be inserted via plugins. A set of default plugins implement these extension points, and the \textit{MultiPoint} configuration mechanism simplifies the management of extension points across multiple plugins. Under this model, a plugin can be enabled once and applied across multiple extension points, while explicit per-extension-point settings (such as disabling a plugin or overriding its weight) take precedence when both are defined.

Despite this extensibility, the default scheduler assumes a homogeneous environment with stable resources \cite{liu2024dynamic}. It bases placement decisions on the resource \textit{requests} declared by containers rather than the actual dynamic load of nodes, which can result in significant load imbalances in heterogeneous edge environments. Furthermore, the default scheduler performs no anomaly detection and therefore cannot make intelligent decisions informed by emerging node-level problems or its own past scheduling inefficiencies \cite{fritzsche2024lightweight}.

For edge deployments, the full Kubernetes distribution carries considerable operational overhead---in terms of binary size, memory footprint, and the complexity of its dependencies---that is difficult to justify on resource-constrained hardware. K3s is a lightweight, CNCF-certified Kubernetes distribution designed specifically for such environments \cite{k3sArchitectureDocs}. It achieves a substantially smaller footprint by packaging required dependencies into a single binary, replacing etcd with a lighter datastore (SQLite or embedded etcd), automating TLS management, and abstracting control plane complexity to simplify cluster operations \cite{k3sArchitectureDocs}. K3s is architecturally compatible with standard Kubernetes APIs, enabling workloads and tooling designed for full Kubernetes to run without modification. Its suitability for resource-constrained and remote locations---including Raspberry Pis, IoT gateways, and edge servers---makes it a natural choice for simulating edge cluster environments. The experimental cluster in this project is built on K3s and is described in Chapter~\ref{chapter2}.

\subsection{Machine Learning in Resource Management}

Machine learning techniques have been applied to several aspects of resource management in cloud and edge systems. This section reviews three relevant areas: anomaly detection, workload prediction, and integration with orchestration platforms.

\subsubsection{Anomaly Detection for Resource Monitoring}

The simplest approaches---\textit{threshold-based} detection and \textit{z-score} detection---flag metrics that fall outside fixed or statistically derived bounds. Both are computationally trivial, but they operate on single metrics independently, making them insensitive to the correlated, multi-dimensional deviations that characterise edge resource anomalies (e.g.\ simultaneous CPU and memory exhaustion).

\textit{K-means clustering} groups observations into $k$ clusters and classifies points whose distance to the nearest centroid exceeds a training-derived threshold as anomalous. K-means is computationally inexpensive and requires no labelled anomaly examples, but its reliance on a global distance threshold makes it sensitive to baseline variance: in noisy edge telemetry, normal-period variance can push the threshold above genuine anomaly distances, suppressing detection \cite{fritzsche2024lightweight}.

The \textit{Negative Selection Algorithm} (NSA), inspired by the biological immune system, is a one-class method that generates detectors in regions of feature space that do not overlap with normal training data; any observation falling within a detector's radius is classified as anomalous. NSA is well-suited to edge scheduling because it requires only normal-behaviour training data (avoiding the impracticality of labelling anomalies in production), provides multi-dimensional classification that captures correlated resource deviations, and maintains a lightweight inference profile. Fritzsche et al.\ demonstrated that NSA substantially outperforms K-means on edge Kubernetes telemetry, particularly because it defines the \textit{boundary} of normal behaviour rather than relying on distance from cluster centres \cite{fritzsche2024lightweight}.

\subsubsection{Time-Series Prediction for Resource Utilisation}

Proactive scheduling requires forecasting future node load so that placement decisions anticipate demand rather than react to it. Existing prediction methods span a wide complexity range, but suitability for edge scheduling depends on the trade-off between forecast quality and computational cost.

\textit{ARIMA} models capture linear temporal dependencies with minimal parameter overhead, and Calheiros et al.\ showed they enable proactive cloud provisioning that reduces over-allocation \cite{calheiros2015arima}. However, ARIMA assumes stationarity and struggles with the abrupt workload transitions common in edge environments, where stress events cause sharp, non-linear metric shifts.

\textit{LSTM-RNN} architectures model long-term non-linear patterns and achieve strong accuracy on complex cloud workloads \cite{kumar2017lstm}, but their memory footprint and training cost are difficult to justify on resource-constrained edge nodes where the predictor must run alongside application workloads. Google's \textit{Autopilot} system demonstrates production-scale ML-driven autoscaling that reduces resource slack \cite{rzadca2020autopilot}, but it targets data-centre environments with ample compute for model inference---an assumption that does not hold at the edge.

Evolutionary Neural Networks (ENNs) automate architecture search through mutation and fitness evaluation, potentially yielding tailored predictors, but their optimisation cost makes them impractical for continuous edge deployment.

These methods collectively establish that prediction improves scheduling quality, but the heavier approaches (LSTM, ENN, large-scale production systems) are poorly matched to edge constraints. This motivates lightweight regression models---such as sliding-window linear or ridge regressors---that deliver short-horizon forecasts within the computational budget of modest edge hardware while remaining compatible with per-second scheduling decisions.

\subsubsection{Integration with Orchestration}

Integrating ML into orchestration requires balancing adaptiveness with the overhead and data demands of the learning approach.

\textit{Reinforcement learning} (RL) schedulers learn placement policies through trial-and-error, optimising objectives such as latency and throughput. Song et al.\ proposed DQKS, a pluggable Kubernetes scheduler using Double Deep Q-Networks that adapts to changing workloads \cite{song2025dqks}, and Benedetti et al.\ demonstrated RL-based autoscaling for serverless edge applications \cite{benedetti2022reinforcement, pattan2025reinforcement}. RL's strength is its ability to discover non-obvious policies without explicit modelling; however, it requires extensive exploration episodes to converge, making it impractical in small edge clusters where each poor scheduling decision directly impacts limited resources and the exploration budget is constrained.

\textit{Predictive autoscaling} incorporates workload forecasts to pre-emptively adjust resource allocations \cite{toka2021scaling, pranata2023serverless}. This addresses the backward-looking limitation of reactive heuristics, but focuses on \textit{scaling}---adjusting the number or size of workloads---rather than \textit{placement}---choosing which node to assign a workload to. In edge clusters with few heterogeneous nodes, placement quality matters as much as scaling.

\textit{Anomaly-triggered rescheduling} relocates pods when anomalies are detected, acting before node failure rather than after degradation \cite{mdemaya2020hercule}. This is effective for long-running services, but in edge environments with short-lived workloads, the cost of migration may exceed the benefit; it is more efficient to make anomaly-aware placement decisions \textit{at scheduling time} rather than correcting them retroactively.

\subsection{Limitations of Existing Methods}

The reviewed literature reveals a progression of increasingly sophisticated approaches to resource management in edge environments, each addressing shortcomings of its predecessors, yet none fully meeting the requirements of lightweight, intelligent scheduling for edge Kubernetes clusters.

Static schedulers ignore runtime state entirely, lacking the contextual awareness necessary for informed decisions in dynamic edge environments. Reactive heuristics improve upon this by incorporating observed resource metrics into scheduling decisions, but they respond to past states rather than anticipating future conditions, causing them to lag behind transient workloads and over-react to short-lived noise \cite{pashaeehir2025kubedsm}.

Anomaly detection methods represent a further improvement by distinguishing genuine workload deviations from normal fluctuations, particularly in variable edge environments. However, detection alone is insufficient---identifying that a node is behaving anomalously does not directly translate into better scheduling decisions without a mechanism to act on that information \cite{fritzsche2024lightweight}.

Prediction models take a proactive approach by forecasting future resource utilisation, enabling pre-emptive scheduling decisions. Yet prediction without anomaly awareness risks placing workloads on nodes that are currently experiencing---or are about to experience---abnormal conditions not captured by the prediction model alone.

What remains absent in the literature is a lightweight system that \textit{combines} anomaly detection with resource prediction to directly inform scheduling decisions. Such a system would detect current deviations from normal behaviour while simultaneously forecasting future node utilisation, providing the scheduler with both reactive and proactive intelligence.
