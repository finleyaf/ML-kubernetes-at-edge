\chapter{Methodology}
\label{chapter3}

\section{Methodology Overview}

This chapter defines the final methodological design used to build and evaluate an anomaly-aware lightweight scheduling pipeline for edge Kubernetes environments. The replication studies in Appendix~\ref{chapter2} established the anomaly-source evidence base and clarified preprocessing sensitivity. Building on that foundation, the present methodology separates offline development from final live evaluation. Offline replay is used to justify detector choice, train and validate the predictor, and audit the locked hybrid policy on historical telemetry. The final scheduler comparison is then made through an authoritative matched-arm experiment on a live heterogeneous K3s cluster.

The methodological principle is simple: no online outcome is used to tune the final policy after the authoritative experiment protocol is fixed. The offline stage therefore informs the core policy family, while the online stage provides the dissertation-grade scheduler comparison claim.

\subsection{Research Questions and Hypotheses}

The methodology addresses three research questions:

\begin{itemize}
\item \textbf{RQ1:} Can a custom anomaly-aware, prediction-informed scheduler improve placement quality compared to the default Kubernetes scheduler in an edge cluster?
\item \textbf{RQ2:} Can those improvements be achieved while preserving low scheduling overhead suitable for edge settings?
\item \textbf{RQ3:} Does the locked hybrid policy family transfer from offline replay audit to online deployment against the default scheduler?
\end{itemize}

These questions are operationalised through the following hypotheses:

\begin{itemize}
\item \textbf{H1:} The custom scheduler improves safe placement rate and reduces anomalous or highly contended placement compared to the default Kubernetes scheduler.
\item \textbf{H2:} The custom scheduler does not introduce practically significant scheduling latency or pod startup time overhead.
\item \textbf{H3:} The locked hybrid policy family yields positive utility delta when deployed online against the default scheduler across repeated matched-arm trials.
\end{itemize}


\section{System and Data Method}

\subsection{End-to-End Experimental Pipeline}

The implemented pipeline is organised into two linked stages.

\textbf{Offline development and audit stage.}

\begin{enumerate}
\item \textbf{Run generation and telemetry capture.} Campaign plans are generated and executed by \texttt{run\_campaign.py}. Each run contains baseline, stress, and recovery phases. Netdata telemetry is collected at one-second intervals by \texttt{netdata\_collector.py}.
\item \textbf{Phase labelling and dataset governance.} Phase timestamps are recorded to \texttt{phases.json}, after which node-aware labels are written to \texttt{labelled.csv}. Only valid runs with complete artifacts are admitted to downstream processing.
\item \textbf{Predictor training and validation.} \texttt{train\_predictor.py} trains per-node regressors using leakage-safe scaling and post-fit calibration. Predictor quality is validated independently of scheduler outcomes.
\item \textbf{Locked replay audit.} \texttt{offline\_policy\_evaluation.py} replays prediction-only, anomaly-only, and hybrid policies on historical telemetry using the locked final policy family defaults. This stage is treated as an offline audit surface rather than as an open-ended online-informed tuning loop.
\end{enumerate}

\textbf{Authoritative online evaluation stage.}

\begin{enumerate}
\setcounter{enumi}{4}
\item \textbf{Capacity export and warm-up seeding.} Before the live comparison begins, allocatable node capacities are exported from the cluster and the custom arm's telemetry history is seeded with warm-up snapshots.
\item \textbf{Pre-decision ranking and authoritative binding.} For each custom-arm placement, a one-shot telemetry snapshot is captured, appended to the custom history, scored by \texttt{rank\_live.py}, and persisted as a ranking JSON. The resulting best node is then applied authoritatively through \texttt{spec.nodeName} before default scheduling can intervene.
\item \textbf{Matched-arm execution and analysis.} \texttt{run\_stage\_b\_matched\_arms.sh} delegates to the authoritative runner, executes counterbalanced default and custom arms across repeated trials, and writes enriched CSV, metadata, and summary artifacts for final analysis.
\end{enumerate}

This design preserves the information barrier between offline development and final online evaluation while also recognising that the final live protocol requires fixed execution refinements that do not exist in offline replay alone, most notably workload-aware capacity pressure, explicit warm-up, and authoritative rank-and-pin binding.


\subsection{Run Construction, Labelling, and Dataset Governance}

Each campaign run writes a dedicated directory containing raw telemetry, labels, phase metadata, and collector logs. A run is considered valid for downstream processing only if both \texttt{labelled.csv} and \texttt{phases.json} are present.

Labelling is phase-aware and node-aware: during a stress phase, only the targeted node is labelled anomalous. This preserves causal alignment between injected stress and anomaly labels. Control-node telemetry is collected for full-cluster observability, but worker-only filtering is applied for scheduler-oriented evaluation because workload placement decisions are made on worker nodes.

Governance rules were enforced as follows:

\begin{itemize}
\item \textbf{Split locking.} Strict holdout runs are fixed in split configuration and excluded from development-stage replay audit.
\item \textbf{Inclusion criteria.} Runs missing required artifacts are excluded from model and evaluation input.
\item \textbf{Operational repair policy.} Interrupted collections are resumed from a specified run index; invalid partial runs are removed before retry.
\end{itemize}

Telemetry collection was conducted in two phases. The first phase produced 20 runs (\texttt{run\_001} to \texttt{run\_020}) using standard stress sequences with gradual transitions. The second phase produced a further 20 runs (\texttt{run\_023} to \texttt{run\_042}) using deliberately abrupt stress sequences to broaden coverage and probe robustness under non-smooth workload transitions. Together, these 40 runs form the telemetry corpus used for predictor training, replay audit, and locked-policy checking. They do not by themselves constitute the final scheduler comparison, which is reserved for the live matched-arm study.


\subsection{Feature Engineering and Preprocessing Choices}

The predictor and live ranker consume five telemetry features per node: \texttt{cpu\_user}, \texttt{cpu\_system}, \texttt{ram\_used}, \texttt{net\_received}, and \texttt{net\_sent}. For the replication appendix (Appendix~\ref{chapter2}), these are also aggregated into CPU and NET composites where required by the detector studies.

Preprocessing differs by stage:

\begin{itemize}
\item \textbf{Replication stage.} Rolling-mean smoothing and min-max normalisation are used to study detector separability under realistic edge noise.
\item \textbf{Prediction stage.} Leakage-safe scaling is applied by fitting the scaler on the training period only and then transforming the full sequence for window construction.
\item \textbf{Live Stage B stage.} Recent telemetry snapshots are ranked directly from Netdata-derived features, while workload requests and exported node capacities are injected only at decision time as execution context rather than as learned time-series features.
\end{itemize}

This separation is intentional. Detector replication addresses anomaly separability, predictor training addresses forecasting adequacy, and the final live stage combines both with workload-aware placement constraints.


\section{Predictive Modeling Method}

\subsection{Predictor Design and Training Protocol}
\label{sec:predictor-design}

The predictor is a lightweight sliding-window regression model trained per worker node. The implementation supports linear and ridge regression; ridge (\(\alpha=1.0\)) was used in the final trained artifact, with window \(w=5\) and horizon \(h=3\).

Given input sequence \(x_t\), training windows are formed as:

\[
X_i = [x_i, x_{i+1}, \dots, x_{i+w-1}], \quad y_i = x_{i+w+h-1}
\]

where each \(x_t\) contains the five telemetry features. Training uses:

\begin{itemize}
\item \textbf{Leakage-safe split:} temporal split before scaling, with scaler fit on the training period only.
\item \textbf{Phase-aware weighting:} CPU and mixed stress targets receive higher sample weights because scheduling decisions during stressed operation are more important than during quiescent operation.
\item \textbf{Post-fit calibration:} per-feature linear correction \(\hat{y}' = a\hat{y} + b\) learned on a calibration tail of the training data.
\end{itemize}

This model family was selected to preserve low inference cost while retaining sufficient short-horizon expressiveness for scheduler ranking. Rolling-origin cross-validation on the development corpus identified the \((w{=}5, h{=}3)\) configuration as the best RMSE trade-off, and strict holdout confirmation preserved that ordering against naive baselines.


\subsection{Predictor Evaluation Method (Pre-Scheduler)}

Predictor quality is evaluated independently of scheduler outcomes using MAE, RMSE, and sMAPE:

\begin{itemize}
\item \textbf{MAE:} direct average magnitude error.
\item \textbf{RMSE:} error magnitude with stronger penalty on larger misses.
\item \textbf{sMAPE:} scale-aware relative error for bounded normalised series.
\end{itemize}

This stage validates forecasting adequacy only. Final scheduler claims are made from replay and online placement metrics rather than from predictor error alone.


\section{Hybrid Scheduler Method}

\subsection{Node Risk and Scoring Formulation}

At each decision step, each candidate node receives three signals:

\begin{itemize}
\item \textbf{Base predicted load} from the node predictor.
\item \textbf{Anomaly risk} from a lightweight detector monitor.
\item \textbf{Workload-capacity penalty} derived from the pod request and the node's allocatable CPU and memory.
\end{itemize}

If the predictor is not yet ready, or if a node lacks trained predictor artifacts, a bounded fallback load estimate is formed from current CPU, RAM, and network observations. This ensures the live ranker continues to operate on heterogeneous worker sets even when model coverage is incomplete.

For node \(i\), let \(\hat{L}_i\) denote base predicted load, \(R_i\) anomaly risk, and \(C_i\) the workload-capacity penalty. The live score is:

\[
\text{score}_i = w_p^{(i)}\,(\hat{L}_i + C_i) + \left(1-w_p^{(i)}\right)R_i
\]

where \(w_p^{(i)}\) is either a fixed prediction weight or an adaptively shifted value based on anomaly risk. The capacity term is defined as:

\[
C_i = \gamma\,\max\!\left(\frac{\text{cpu}_{\text{req}}}{\text{cpu}_{\text{cap},i}},\;\frac{\text{mem}_{\text{req}}}{\text{mem}_{\text{cap},i}}\right)
\]

with \(\gamma\) fixed before the live experiment. Lower total score indicates the preferred placement.

The NSA monitor remains one-class and history-based: each node's recent trajectory defines \textit{self} behaviour, while sampled detectors in non-self regions produce anomaly risk from nearest-detector distance. This preserves continuity with the replication evidence in Appendix~\ref{chapter2}, while the capacity term extends the ranker to heterogeneous live execution.


\subsection{Policy Variants and Final Comparison Surface}

Offline replay retains three internal policies for controlled comparison on identical decision points:

\begin{itemize}
\item \textbf{Prediction-only:} \(w_p=1.0\), anomaly weight \(=0.0\).
\item \textbf{Anomaly-only:} \(w_p=0.0\), anomaly weight \(=1.0\).
\item \textbf{Hybrid:} fixed high-prediction-weight policy with anomaly correction.
\end{itemize}

For the authoritative online comparison, however, the relevant external comparison is between:

\begin{itemize}
\item \textbf{Default arm:} pods are left to the unmodified Kubernetes \texttt{default-scheduler}.
\item \textbf{Custom arm:} the Python ranker computes the best node from live telemetry, workload requests, and node capacities, after which the pod is bound authoritatively via \texttt{spec.nodeName} before default scheduling can make the placement decision.
\end{itemize}

This distinction is important. The offline stage compares internal policies on replayed telemetry. The online stage compares the locked hybrid policy against the default scheduler through an equivalent authoritative binding path.


\section{Evaluation Protocol}

\subsection{Offline Policy Locking and Replay Audit}
\label{sec:offline-selection}

The final report treats offline evaluation as a locked replay audit aligned to the final live policy family. NSA is retained as the anomaly source on the basis of the replication evidence in Appendix~\ref{chapter2}, and the offline defaults are fixed to the same family used online:

\begin{itemize}
\item predictor window \(= 5\)
\item warm-up \(= 24\) observations
\item anomaly history \(= 45\)
\item anomaly source \(=\) NSA
\item prediction weight \(= 0.9\)
\item anomaly weight \(= 0.1\)
\item NSA detector budget \(= 120\)
\item NSA detector radius \(= 0.9\)
\end{itemize}

The replay objective remains the protocol-defined utility:

\[
U = 0.45\,\text{safe} - 0.25\,\text{anom} - 0.15\,\text{contention} - 0.10\,\text{latency} + 0.05\,\text{fairness}
\]

with tie-breakers favouring higher safe placement, fewer anomalies, lower contention, better fairness, and lower latency. This locked replay stage is used to confirm that the chosen hybrid family remains preferable to the prediction-only baseline on historical telemetry without reopening a broad online-informed search surface.


\subsection{Locked Custom Scheduler Configuration}

After offline development, the following parameters were frozen for the final live experiment:

\begin{itemize}
\item anomaly source \(=\) NSA
\item prediction weight \(= 0.9\)
\item anomaly weight \(= 0.1\)
\item anomaly history \(= 45\)
\item warm-up history \(= 24\) one-second snapshots
\item NSA detector budget \(= 120\)
\item NSA detector radius \(= 0.9\)
\end{itemize}

In addition to these core policy parameters, the final live protocol also fixes the execution refinements needed for heterogeneous deployment:

\begin{itemize}
\item workload-aware capacity penalty factor \(= 1.0\)
\item live export of node allocatable CPU and memory
\item one-shot pre-decision telemetry snapshots and persisted ranking artifacts
\item authoritative custom placement through rank-and-pin rather than through a secondary scheduler profile
\end{itemize}

These refinements were fixed before the final experiment and are treated as part of the final online protocol rather than as post hoc tuning.


\subsection{Online Matched-Arm Experiment (Stage B)}

The authoritative comparison between the custom scheduler and the default Kubernetes scheduler is conducted as a matched-arm online experiment on the live K3s cluster. The final cluster comprises a control node and four schedulable worker targets: \texttt{k3s-worker-2}, \texttt{k3s-worker-3}, \texttt{k3s-worker-4}, and \texttt{raspberrypi}. This expands the placement space beyond the earlier two-worker replication environment and introduces explicit heterogeneity into the online study.

\subsubsection{Experimental Design}

Each trial contains a normal phase and three stress phases (CPU, memory, and mixed). For each workload within each phase, the arm order is counterbalanced so that odd-numbered trials execute baseline then custom, while even-numbered trials execute custom then baseline. This reduces the systematic bias introduced by always running one arm first.

The two arms are:

\begin{enumerate}
\item \textbf{Baseline arm.} The workload manifest is submitted without a forced node, leaving the placement decision to \texttt{default-scheduler}.
\item \textbf{Custom arm.} The ranking engine is invoked immediately before submission. It consumes the seeded telemetry history, the newest one-shot snapshot, the workload request extracted from the manifest, and the exported node capacities. The best node is then written into \texttt{spec.nodeName}, making the placement decision authoritative.
\end{enumerate}

Stress profiles are rotated across the worker set to avoid coupling any single resource profile to a single node. A short washout period is inserted after each decision to improve independence between successive placements.

\subsubsection{Workloads}

Three workload types are used in every phase:

\begin{table}[h]
\centering
\begin{tabular}{lll}
\hline
\textbf{Workload} & \textbf{Resource Profile} & \textbf{Container Command} \\
\hline
\texttt{cpu-pod} & CPU-intensive & \texttt{stress --cpu 1 --timeout 60} \\
\texttt{memory-pod} & Memory-intensive & \texttt{stress --vm 1 --timeout 60} \\
\texttt{mixed-pod} & CPU + memory & \texttt{stress --cpu 1 --vm 1 --timeout 60} \\
\hline
\end{tabular}
\caption{Workload types used in the final online matched-arm evaluation. Workload requests are parsed from the manifests and supplied directly to the live ranker.}
\label{tab:ch3-workload-types}
\end{table}

With one normal phase and three stress phases per trial, each arm executes 12 pods per trial (three workloads per phase across four phases), for a planned total of 120 pods per arm across 10 trials.

\subsubsection{Metrics Collection}

For each pod, \texttt{collect\_scheduling\_metrics.py} records:

\begin{itemize}
\item scheduling latency
\item startup time
\item total time
\item chosen node
\item high-contention flag
\item anomaly proxy label
\item active phase, stress profile, and stress target
\item expected-node match for authoritative custom decisions
\item workload request metadata
\item decision score, predicted load, anomaly risk, capacity penalty, and prediction source
\item paths to the snapshot CSV and ranking JSON used for the decision
\end{itemize}

The redesigned summary stage then produces aggregate, per-phase, per-workload, and utility-component views from these enriched artifacts.


\section{Software Management and Version Control}

The project was managed using Git with a remote repository hosted on GitHub. Development was organised across three major subsystems: \texttt{offline-replication} for anomaly-detection replication, \texttt{online-telemetry} for live cluster data collection, and \texttt{scheduler-prediction} for prediction, hybrid scoring, offline audit, and online evaluation.

The repository follows a modular directory structure:

\begin{itemize}
\item \texttt{anomaly-detection/offline-replication/} --- synthetic data generation, preprocessing, detection, and evaluation for the offline anomaly study.
\item \texttt{anomaly-detection/online-telemetry/} --- telemetry collection, preprocessing, and live-cluster detection experiments.
\item \texttt{scheduler-prediction/prediction/} --- predictor training, calibration, and validation.
\item \texttt{scheduler-prediction/custom-scheduler/} --- hybrid scheduler, offline replay audit, and live ranking engine.
\item \texttt{scheduler-prediction/baseline/} --- workload manifests and metric-collection helpers for scheduler comparison.
\item \texttt{scheduler-prediction/online/} --- authoritative matched-arm runner, analysis scripts, cluster configuration, and result artifacts.
\item \texttt{report/} --- \LaTeX{} report source.
\end{itemize}

Configuration files, evaluation protocols, environment templates, and saved model directories are version-controlled alongside the code they configure. This preserves reproducibility without relying on external documentation.


\section{Methodology Summary}

This chapter defined a two-stage methodology for evaluating a lightweight anomaly-aware scheduler against the default Kubernetes scheduler in an edge cluster setting. Offline work established detector choice, trained and validated the predictor, and audited the locked hybrid policy family on replayed telemetry. The final scheduler claim is reserved for the authoritative online matched-arm experiment, which uses explicit warm-up, workload-aware capacity scoring, counterbalanced arm order, multiple stress profiles, rotating stress targets, and authoritative rank-and-pin placement on a heterogeneous live cluster. The next chapter describes the implemented system and the readiness validation completed before the final experiment is executed.
