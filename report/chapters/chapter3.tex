\chapter{Methodology}
\label{chapter3}

\section{Methodology Overview}

This chapter defines the methodological design used to build and evaluate the final anomaly-aware lightweight prediction scheduling pipeline for edge Kubernetes environments. It explains the system design, cluster environment, data-governance rules, predictor and policy-locking path, and the online protocol used for the final scheduler claim. The replication studies that justify anomaly-source selection and preprocessing choices are documented separately in Appendix~\ref{chapter2}.

\subsection{System Design}

The system is a custom scheduler built from two decision signals. The first is a short-horizon resource predictor that estimates near-future node load from recent telemetry windows. The second, retained on the basis of the replication evidence in Appendix~\ref{chapter2}, is a runtime NSA-based anomaly monitor that estimates whether a node is behaving abnormally from recent telemetry history. At decision time these signals are combined with workload-size, capacity, contention, and safety terms to produce a ranked list of feasible nodes.

\subsection{Research Questions and Hypotheses}

The methodology addresses primary and secondary research questions which motivate the end-to-end pipeline:

\begin{itemize}
\item \textbf{RQ1:} Can a custom anomaly-aware, prediction-informed scheduler improve placement quality compared to the default Kubernetes scheduler in an edge cluster?
\item \textbf{RQ2:} Can those improvements be achieved while preserving low scheduling overhead suitable for edge settings?
\item \textbf{RQ3:} Does the locked hybrid policy family transfer from offline replay audit to online deployment against the default scheduler?
\item \textbf{SRQ1:} In a supplementary Pi-inclusive extension, can the locked custom arm be exposed to a heterogeneous worker pool through workload-specific eligibility without collapsing into blanket Pi usage or blanket Pi avoidance?
\end{itemize}

These questions are operationalised through the following hypotheses:

\begin{itemize}
\item \textbf{H1:} The custom scheduler improves safe placement rate and reduces anomalous or highly contended placement compared to the default Kubernetes scheduler.
\item \textbf{H2:} The custom scheduler does not introduce practically significant scheduling latency or pod startup time overhead.
\item \textbf{H3:} The locked hybrid policy family yields positive utility delta when deployed online against the default scheduler across repeated matched-arm trials.
\end{itemize}

SRQ1 is treated as exploratory rather than claim-bearing. The dissertation's confirmatory scheduler result is therefore tied only to H1--H3 on the homogeneous-worker Stage B comparison, while any Pi-inclusive extension is interpreted as supplementary compatibility or limitation evidence.

\subsection{End-to-End Pipeline}

The implemented pipeline is organised into two linked stages.

\textbf{Offline development}
\begin{enumerate}
\item \textbf{Telemetry collection and preprocessing.} A governed telemetry corpus is collected from the live K3s cluster, cleaned, labelled, and filtered to preserve only runs with the required artifacts and worker coverage.
\item \textbf{Predictor training and validation.} Per-node lightweight regressors are trained on the governed development slice using leakage-safe scaling, phase-aware weighting, and post-fit calibration; their adequacy is checked on a strict holdout split before any live claim is made.
\item \textbf{Locked policy selection.} Internal prediction-only, anomaly-only, and hybrid policies are compared under replay audit, and a single safety-priority hybrid configuration is frozen before online deployment.
\end{enumerate}

\textbf{Online evaluation}
\begin{enumerate}
\setcounter{enumi}{3}
\item \textbf{Claim-bearing Stage B configuration.} The final comparison path is fixed to a homogeneous three-worker subset shared by both arms, with identical workload eligibility and counterbalanced trial order.
\item \textbf{Matched-arm execution and analysis.} Baseline and custom arms are executed on the live cluster, per-decision artifacts are retained, and the final summary is generated from the resulting scheduling traces.
\end{enumerate}

\section{Cluster and Data Pipeline}

\subsection{Cluster Environment}

The live K3s cluster comprised a control node (\texttt{k3s-control}), three cloud worker nodes (\texttt{k3s-worker-2}, \texttt{k3s-worker-3}, and \texttt{k3s-worker-4}), and a Raspberry Pi 5 worker (\texttt{raspberrypi}). This full topology is heterogeneous by design and was used for telemetry collection, predictor coverage, and supplementary Pi-inclusive checks. However, the authoritative scheduler claim is restricted to the homogeneous cloud-worker subset \texttt{k3s-worker-2}, \texttt{k3s-worker-3}, and \texttt{k3s-worker-4}, because that keeps the baseline comparison on a common and methodologically defensible feasible set.

K3s was used as the Kubernetes distribution in place of the full upstream package. As described in Section~\ref{chapter1}, K3s is designed specifically for resource-constrained and remote environments, which makes it a closer approximation of realistic edge cluster hardware than a standard Kubernetes installation on cloud VMs.

Netdata was selected as the telemetry platform because it is built for edge-first deployment: it delivers per-second metric precision, maintains a minimal CPU and memory footprint during collection, and operates autonomously when upstream connectivity is interrupted. A Netdata agent runs on each node, while a parent instance on the control-plane side aggregates cluster telemetry for the collection scripts. During live experiments, that parent endpoint is exposed to the local operator environment through SSH port forwarding so that the same per-second collector can be used across offline pipeline rebuilding and online matched-arm evaluation.

Operational access to the distributed cluster was maintained through Google Cloud SSH for the cloud VMs and Tailscale as the private remote-access layer spanning the cloud nodes, the Raspberry Pi, and the local operator environment. This access path supports experiment execution and telemetry retrieval, but it is not part of the scheduler decision signal itself.

Each run writes a dedicated directory containing raw telemetry, labels, phase metadata, and collector logs.

Labelling is phase-aware and node-aware: during a stress phase, only the targeted node is labelled anomalous. This preserves causal alignment between injected stress and anomaly labels. Control-node telemetry is collected for full-cluster observability, but worker-only filtering is applied for scheduler-oriented evaluation because workload placement decisions are made on worker nodes.

Governance rules were enforced as follows:

\begin{itemize}
\item \textbf{Split locking.} Strict holdout runs are fixed in split configuration and excluded from development-stage replay audit.
\item \textbf{Inclusion criteria.} Runs missing required artifacts are excluded from model and evaluation input.
\item \textbf{Operational repair policy.} Interrupted collections are resumed from a specified run index; invalid partial runs are removed before retry.
\end{itemize}

For the final predictor and replay path, the governed fair-cohort split fixed \texttt{run\_043}--\texttt{run\_051} as development data and \texttt{run\_052}--\texttt{run\_055} as strict holdout. This prevents the final online protocol from being tuned directly on the same late-run corpus used to confirm transfer.

\subsection{Feature Engineering and Preprocessing Choices}

The predictor and live ranker consume five telemetry features per node: \texttt{cpu\_user}, \texttt{cpu\_system}, \texttt{ram\_used}, \texttt{net\_received}, and \texttt{net\_sent}. For the replication appendix (Appendix~\ref{chapter2}), these are also aggregated into CPU and NET composites where required by the detector studies.

Preprocessing differs by stage:

\begin{itemize}
\item \textbf{Replication stage.} Rolling-mean smoothing and min-max normalisation are used to study detector separability under realistic edge noise.
\item \textbf{Prediction stage.} Leakage-safe scaling is applied by fitting the scaler on the training period only and then transforming the full sequence for window construction.
\item \textbf{Online evaluation stage.} Recent telemetry snapshots are ranked directly from Netdata-derived features, while workload requests and exported node capacities are injected only at decision time as execution context rather than as learned time-series features.
\end{itemize}

This separation is intentional. Detector replication addresses anomaly separability, predictor training addresses forecasting adequacy, and online evaluation combines both with workload-aware placement constraints.

\section{Predictive Modelling Method}

\subsection{Predictor Design and Training Protocol}
\label{sec:predictor-design}

The predictor is a lightweight sliding-window regression model trained per worker node. The implementation supports linear and ridge regression; ridge (\(\alpha=1.0\)) was used in the final trained artifact, with window \(w=5\) and horizon \(h=3\).

Given input sequence \(x_t\), training windows are formed as:

\[
X_i = [x_i, x_{i+1}, \dots, x_{i+w-1}], \quad y_i = x_{i+w+h-1}
\]

where each \(x_t\) contains the five telemetry features. Training uses:

\begin{itemize}
\item \textbf{Leakage-safe split:} temporal split before scaling, with scaler fit on the training period only.
\item \textbf{Phase-aware weighting:} CPU and mixed stress targets receive higher sample weights because scheduling decisions during stressed operation are more important than during quiescent operation.
\item \textbf{Post-fit calibration:} per-feature linear correction \(\hat{y}' = a\hat{y} + b\) learned on a calibration tail of the training data.
\end{itemize}

This model family was selected to preserve low inference cost while retaining sufficient short-horizon expressiveness for scheduler ranking. Rolling-origin cross-validation on the development corpus identified the \((w{=}5, h{=}3)\) configuration as the best RMSE trade-off, and strict holdout confirmation preserved that ordering against naive baselines.


\subsection{Predictor Evaluation Method (Pre-Scheduler)}

Predictor quality is evaluated independently of scheduler outcomes using MAE, RMSE, and sMAPE:

\begin{itemize}
\item \textbf{MAE:} direct average magnitude error.
\item \textbf{RMSE:} error magnitude with stronger penalty on larger misses.
\item \textbf{sMAPE:} scale-aware relative error for bounded normalised series.
\end{itemize}

This stage validates forecasting adequacy only. Final scheduler claims are made from replay and online placement metrics rather than from predictor error alone.


\section{Hybrid Scheduler Method}

\subsection{Node Risk and Scoring Formulation}

At each decision step, each candidate node receives three signals:

\begin{itemize}
\item \textbf{Base predicted load} from the node predictor.
\item \textbf{Anomaly risk} from a lightweight detector monitor.
\item \textbf{Workload-capacity penalty} derived from the pod request and the node's allocatable CPU and memory.
\end{itemize}

If the predictor is not yet ready, or if a node lacks trained predictor artifacts, a bounded fallback load estimate is formed from current CPU, RAM, and network observations. This ensures the live ranker continues to operate on the selected worker set even when model coverage is incomplete.

For node \(i\), let \(\hat{L}_i\) denote base predicted load, \(R_i\) anomaly risk, \(C_i\) the workload-capacity penalty, and \(\rho_i\) the observed relative CPU load at decision time. The live score is:

\[
\text{score}_i = w_p^{(i)}\,(\hat{L}_i + C_i) + \left(1-w_p^{(i)}\right)R_i + P_i^{\text{cont}} + P_i^{\text{safe}}
\]

where \(w_p^{(i)}\) is either a fixed prediction weight or an adaptively shifted value based on anomaly risk. The capacity term is defined as:

\[
C_i = \gamma\,\max\!\left(\frac{\text{cpu}_{\text{req}}}{\text{cpu}_{\text{cap},i}},\;\frac{\text{mem}_{\text{req}}}{\text{mem}_{\text{cap},i}}\right)
\]

with \(\gamma\) fixed before the live experiment. Explicit contention and safety penalties are then applied from the observed relative CPU level:

\[
P_i^{\text{cont}} = \lambda_c\,\max(0, \rho_i - \tau_c), \qquad
P_i^{\text{safe}} = \lambda_s\,\max(0, \rho_i - \tau_s)
\]

where \(\tau_c\) and \(\tau_s\) are the locked contention and safety thresholds, and \(\lambda_c\) and \(\lambda_s\) are the corresponding penalty factors. Lower total score indicates the preferred placement. When at least one node remains below the safety threshold, nodes above that threshold are additionally deprioritised through unsafe-node avoidance.

The NSA monitor remains one-class and history-based: each node's recent trajectory defines \textit{self} behaviour, while sampled detectors in non-self regions produce anomaly risk from nearest-detector distance. This preserves continuity with the replication evidence in Appendix~\ref{chapter2}, while the capacity and observed-load terms extend the ranker to live workload placement.


\subsection{Policy Variants and Final Comparison Surface}

Offline replay retains three internal policies for controlled comparison on identical decision points:

\begin{itemize}
\item \textbf{Prediction-only:} \(w_p=1.0\), anomaly weight \(=0.0\).
\item \textbf{Anomaly-only:} \(w_p=0.0\), anomaly weight \(=1.0\).
\item \textbf{Hybrid:} prediction-led scoring with anomaly correction, workload-capacity pressure, and explicit observed-load safety penalties.
\end{itemize}

For the authoritative online comparison, however, the relevant external comparison is between:

\begin{itemize}
\item \textbf{Default arm:} pods are left to the unmodified Kubernetes \texttt{default-scheduler}.
\item \textbf{Custom arm:} the Python ranker computes the best node from live telemetry, workload requests, and node capacities, after which the pod is bound authoritatively via \texttt{spec.nodeName} before default scheduling can make the placement decision.
\end{itemize}

This distinction is important. The offline stage compares internal policies on replayed telemetry. The online stage compares the locked hybrid policy against the default scheduler through an equivalent authoritative binding path.


\section{Evaluation Protocol}

\subsection{Offline Policy Locking and Replay Audit}
\label{sec:offline-selection}

The final report treats offline evaluation as a locked replay audit aligned to the final live policy family. NSA is retained as the anomaly source on the basis of the replication evidence in Appendix~\ref{chapter2}, and the offline defaults are fixed to the same family used online. A dedicated safety-priority replay protocol was then used to select the final live configuration before the authoritative run was executed. Table~\ref{tab:ch3-replay-locking} summarises the replay settings that were held fixed during this audit.

\begin{table}[h]

\hline

\label{tab:ch3-replay-locking}

The replay objective remains the protocol-defined utility:

\[
U = 0.45\,\text{safe} - 0.25\,\text{anom} - 0.15\,\text{contention} - 0.10\,\text{latency} + 0.05\,\text{fairness}
\]

with tie-breakers favouring higher safe placement, fewer anomalies, lower contention, better fairness, and lower latency. This locked replay stage is used to confirm that the chosen hybrid family remains preferable to simpler alternatives on historical telemetry without reopening a broad online-informed search surface.

\subsection{Online Matched-Arm Experiment (Stage B)}

The authoritative comparison between the custom scheduler and the default Kubernetes scheduler is conducted as a matched-arm online experiment on the live K3s cluster. The physical platform contains a control node and multiple workers, but the final scheduler claim is restricted to the homogeneous worker subset \texttt{k3s-worker-2}, \texttt{k3s-worker-3}, and \texttt{k3s-worker-4}. This keeps both arms on the same feasible worker pool and makes the default scheduler baseline easier to interpret in light of its reliance on comparatively homogeneous resources \cite{liu2024dynamic}.

\subsubsection{Experimental Design}

Each trial contains a normal phase and three stress phases (CPU, memory, and mixed). For each workload within each phase, the arm order is counterbalanced so that odd-numbered trials execute baseline then custom, while even-numbered trials execute custom then baseline. This reduces the systematic bias introduced by always running one arm first.

The two arms are:

\begin{enumerate}
\item \textbf{Baseline arm.} The workload manifest is submitted with worker-pool eligibility constraints but without a forced node, leaving the placement decision to the unmodified \texttt{default-scheduler}.
\item \textbf{Custom arm.} The ranking engine is invoked immediately before submission. It consumes the seeded telemetry history, the newest one-shot snapshot, the workload request extracted from the manifest, and the exported node capacities. The best node is then written into \texttt{spec.nodeName}, making the placement decision authoritative while preserving the same eligible worker set used by the baseline arm.
\end{enumerate}

Stress profiles are rotated across the worker set to avoid coupling any single resource profile to a single node. A short washout period is inserted after each decision to improve independence between successive placements.

Three workload types are used in every phase:

With one normal phase and three stress phases per trial, each arm executes 12 pods per trial (three workloads per phase across four phases), for a planned total of 120 pods per arm across 10 trials.

\subsubsection{Supplementary Pi-Inclusive Extension}

After the claim-bearing Stage B path had been fixed, a supplementary Pi-inclusive extension was defined to test heterogeneous compatibility without reopening the main baseline comparison. In that extension, the Raspberry Pi remained in the cluster-wide telemetry and model set, but workload eligibility was made workload-specific: standard workloads (\texttt{cpu-pod}, \texttt{memory-pod}, and \texttt{mixed-pod}) remained restricted to the three cloud workers, while lighter Pi-fit workloads (\texttt{cpu-lite-pod}, \texttt{memory-lite-pod}, and \texttt{mixed-lite-pod}) were allowed to consider \texttt{raspberrypi} as an eligible node.

This design was chosen specifically to avoid the earlier methodological failure mode in which a Pi-inclusive baseline could collapse into uninformative blanket placement on the weakest worker. The supplementary extension is therefore interpreted as feasibility and limitation evidence about heterogeneous support, not as a replacement for the homogeneous final comparison.

\subsubsection{Metrics Collection}

For each pod, \texttt{collect\_scheduling\_metrics.py} records timing metrics (scheduling latency, startup time, and total time), placement metadata (chosen node, phase, stress profile, stress target, and workload request), safety labels (high-contention flag, anomaly proxy label, and expected-node match), and decision diagnostics (score, predicted load, anomaly risk, capacity penalty, prediction source, and the paths to the snapshot CSV and ranking JSON used for the decision).

The final summary stage then produces aggregate, per-phase, per-workload, and utility-component views from these enriched artifacts.


\section{Software Management and Version Control}

The project was managed using Git with a remote repository hosted on GitHub. Development was organised across three major subsystems: \texttt{offline-replication} for anomaly-detection replication, \texttt{online-telemetry} for live cluster data collection, and \texttt{scheduler-prediction} for prediction, hybrid scoring, offline audit, and online evaluation.

The repository follows a modular directory structure:

\begin{itemize}
\item \texttt{anomaly-detection/offline-replication/} --- synthetic data generation, preprocessing, detection, and evaluation for the offline anomaly study.
\item \texttt{anomaly-detection/online-telemetry/} --- telemetry collection, preprocessing, and live-cluster detection experiments.
\item \texttt{scheduler-prediction/prediction/} --- predictor training, calibration, and validation.
\item \texttt{scheduler-prediction/custom-scheduler/} --- hybrid scheduler, offline replay audit, and live ranking engine.
\item \texttt{scheduler-prediction/baseline/} --- workload manifests and metric-collection helpers for scheduler comparison.
\item \texttt{scheduler-prediction/online/} --- authoritative matched-arm runner, analysis scripts, cluster configuration, and result artifacts.
\item \texttt{report/} --- \LaTeX{} report source.
\end{itemize}

Configuration files, evaluation protocols, environment templates, and saved model directories are version-controlled alongside the code they configure. This preserves reproducibility without relying on external documentation.


\section{Methodology Summary}

This chapter defined a two-stage methodology for evaluating a lightweight anomaly-aware scheduler against the default Kubernetes scheduler in an edge cluster setting. Offline work established detector choice, governed the telemetry corpus, trained and validated the predictor, and audited the locked hybrid policy family on replayed telemetry. The final scheduler claim is reserved for the authoritative online matched-arm experiment, which uses a homogeneous three-worker subset, explicit warm-up, workload-aware capacity scoring, adaptive safety penalties, counterbalanced arm order, multiple stress profiles, rotating stress targets, and authoritative rank-and-pin placement. A supplementary Pi-inclusive extension is methodologically separated from that main claim and treated as heterogeneous compatibility evidence rather than as the dissertation's primary scheduler comparison. The next chapter describes the implemented system and the validation evidence used to justify and check that final protocol.
