\section{Implementation}

This chapter describes the implemented system that supports the final methodology in Chapter~\ref{chapter3}. The emphasis is on the components that are actually on the execution path of the final experiment, rather than on historical alternatives retained in the repository.

\subsection{Predictor Training Pipeline}

The predictor training pipeline (\texttt{train\_predictor.py}) produces per-node regression models from phase-labelled telemetry. The core implementation choices are:

\begin{itemize}
\item \textbf{Leakage-safe scaling.} A temporal split is applied before fitting the scaler, so future statistics cannot influence training features.
\item \textbf{Phase-aware sample weighting.} CPU and mixed stress targets receive higher sample weight because prediction quality during stressed operation is more important than during quiescent operation.
\item \textbf{Post-fit calibration.} Per-feature affine correction is learned on a calibration tail of the training data and applied at inference time.
\item \textbf{Artifact traceability.} Each model directory stores per-node model bundles, scalers, and a \texttt{training\_summary.json} with split sizes and error metrics.
\end{itemize}

These choices are designed to keep inference lightweight while preserving the temporal discipline needed for an honest downstream scheduler evaluation.


\subsection{Runtime Predictor}

The runtime predictor in \texttt{predictor.py} provides the inference interface consumed by the live ranker. \texttt{NodePredictor} manages a per-node sliding buffer, while \texttt{ClusterPredictor} aggregates all worker-specific predictors and exposes cluster-wide prediction.

The scalar predicted-load score is a weighted combination of CPU, RAM, and network forecasts, with CPU and memory receiving the highest weight. Two implementation details are particularly important for the final online experiment:

\begin{itemize}
\item \textbf{Warm-start fallback.} Until the sliding window is full, the ranker falls back to a bounded load estimate derived from current observations.
\item \textbf{Missing-artifact fallback.} If a node does not have a trained model bundle, the cluster predictor records it as a fallback-only node rather than failing the entire ranking path.
\end{itemize}

This fallback behaviour is necessary for the expanded heterogeneous cluster, where model coverage may lag behind topology changes.


\subsection{Anomaly Monitors}

The anomaly-monitor implementation in \texttt{hybrid\_scheduler.py} conforms to a common \texttt{update()}/\texttt{ready()}/\texttt{risk()} interface. Based on the replication evidence in Appendix~\ref{chapter2}, NSA was retained as the deployed anomaly source.

The NSA monitor estimates node-local \textit{self} behaviour from recent history and samples detectors in non-self regions. At inference time, risk is obtained from nearest-detector distance through a bounded logistic mapping. The codebase retains z-score and K-means monitors for completeness, but the final report treats these as alternative implementations rather than as deployed components.


\subsection{Hybrid Scheduler Engine}

The \texttt{HybridScheduler} class combines prediction and anomaly monitoring into a single ranking decision. It now exposes several behaviours that matter directly to the final online protocol:

\begin{itemize}
\item \textbf{Fixed or adaptive weights.} The engine supports either fixed prediction/anomaly weights or anomaly-risk-dependent reweighting.
\item \textbf{Workload-aware capacity pressure.} Each candidate node can receive an additive capacity penalty derived from the workload request and the node's allocatable CPU and memory.
\item \textbf{Prediction provenance.} The returned \texttt{NodeScore} records whether the chosen node used a trained model or a fallback estimate.
\item \textbf{Decision diagnostics.} The returned score structure includes base predicted load, projected load, anomaly risk, request fractions, and capacity penalty.
\end{itemize}

This is the critical implementation change separating the final live ranker from the earlier replay-only formulation: the final online score is workload-aware and heterogeneity-aware at decision time.


\subsection{Offline Replay Audit}

The offline replay evaluator (\texttt{offline\_policy\_evaluation.py}) remains in the repository, but for the final report it is treated as a locked replay audit rather than as a broad search engine. The defaults were aligned to the final live policy family: warm-up 24, anomaly history 45, NSA source, prediction weight 0.9, anomaly weight 0.1, and the same detector budget used online.

This keeps the offline surface methodologically consistent with the final live family while avoiding the need to claim that every live execution refinement was selected in offline replay. The offline stage therefore supports detector choice, predictor adequacy, and locked-family replay audit; it does not replace the final online evaluation.


\subsection{Authoritative Custom Decision Path}

The final online comparison does not rely on a second deployed scheduler profile to attribute decisions to the custom policy. Instead, the authoritative path is implemented directly in the runner:

\begin{enumerate}
\item export live allocatable node capacities from the cluster
\item seed the custom arm with 24 warm-up telemetry samples
\item capture a one-shot snapshot immediately before each custom decision
\item append that snapshot to the custom history
\item invoke \texttt{rank\_live.py} using the locked predictor and NSA configuration, the workload request, and the exported node capacities
\item persist the ranking JSON for later audit
\item bind the pod authoritatively by writing the chosen node into \texttt{spec.nodeName}
\end{enumerate}

This design ensures that the evaluated custom-arm decision is produced by the implemented Python ranker itself. A historical Kubernetes scheduler manifest remains in the repository, but it is not the authority path used for the final dissertation claim.


\subsection{Online Experiment Orchestration}

The final online experiment is orchestrated by \texttt{run\_stage\_b\_authoritative\_rank\_and\_pin.sh}, which is invoked through the historical entry point \texttt{run\_stage\_b\_matched\_arms.sh}. The runner is responsible for:

\begin{itemize}
\item exporting node capacities at the start of the run
\item seeding and maintaining the custom telemetry history
\item counterbalancing arm order by trial
\item rotating stress profiles (CPU, memory, mixed) and stress targets across the worker set
\item extracting workload requests from the pod manifests
\item collecting enriched per-decision metrics and metadata
\item producing redesigned summary output through \texttt{analyse\_stage\_b\_redesigned\_results.py}
\end{itemize}

As a result, the final Stage B artifacts include not only baseline and custom scheduling CSVs, but also decision snapshots, ranking JSONs, node-capacity exports, run metadata, and a redesigned summary JSON.


\section{Validation and Threats to Validity}

\subsection{Predictor Validation}

Predictor selection was performed by rolling-origin cross-validation on the development corpus and confirmed on a strict holdout split. The \((w{=}5, h{=}3)\) configuration remained the best RMSE trade-off against naive baselines, which justified retaining the lightweight linear family for live scheduling.

The final trained artifact also produced comparable error across worker nodes, which supports using a common scoring surface across the live cluster rather than tuning separate policies per node.


\subsection{Offline Replay Validation}

The offline replay path was validated as a locked audit surface aligned to the final live family. This alignment matters because the dissertation no longer relies on an expansive offline search narrative. The replay stage now supports the claim that the chosen hybrid family remains preferable to simpler baselines on historical telemetry, while the final online experiment remains the authoritative placement comparison.


\subsection{Online Pipeline Readiness Validation}

Before executing the final matched-arm experiment, the following readiness checks were completed:

\begin{itemize}
\item \textbf{Runner validation.} Shell syntax checks passed for the redesigned Stage B runners.
\item \textbf{Python validation.} \texttt{py\_compile} passed for the changed ranking, replay, and orchestration modules.
\item \textbf{Ranking smoke checks.} Synthetic validation confirmed that \texttt{rank\_live.py} runs successfully with missing-model fallback behaviour enabled.
\item \textbf{Analysis smoke checks.} The redesigned summary script ran successfully on an existing smoke dataset, and the legacy analysis entry point was reduced to a compatibility wrapper.
\item \textbf{Artifact readiness.} The online collector, metric logger, and analysis scripts now accept and preserve the extra fields required for per-decision telemetry audit.
\end{itemize}

These checks establish pipeline readiness, not final experimental success. Final data-integrity results will be reported only after the authoritative matched-arm run has been executed.

\subsection{Threats to Validity and Mitigations}

\textbf{Internal validity threats.} Live cluster state can drift between arms, telemetry endpoints can fail transiently, and heterogeneous node behaviour can complicate attribution. These threats were mitigated by explicit warm-up, one-shot pre-decision snapshots, persisted decision artifacts, counterbalanced arm order, and fixed washout periods.

\textbf{Construct validity threats.} The final online experiment measures placement safety, anomaly exposure, contention, timing, fairness, and utility under controlled stress injection. These remain proxies for wider edge quality of service, but they are closer to actual placement decisions than predictor error or detector F1 alone.

\textbf{External validity threats.} Even with the expanded worker set, the cluster remains smaller and cleaner than many production edge deployments. K3s on cloud VMs plus one Raspberry Pi is a stronger edge proxy than the earlier two-worker replication cluster, but still not a complete substitute for geographically distributed physical edge fleets.

\textbf{Selection bias threat.} Offline replay influenced the choice of the core hybrid family, but the final live execution refinements were fixed before the online experiment. This reduces the risk of optimistic bias from adapting the method after observing live outcomes.


\subsection{Reproducibility Package}

Reproducibility is supported through code, configuration, and artifact traceability:

\begin{itemize}
\item campaign plans and per-run telemetry artifacts
\item locked model directories with training summaries
\item offline replay audit configuration and outputs
\item workload manifests and metric-collection helpers
\item authoritative online runner, node-capacity export, and redesigned analysis scripts
\item per-decision online artifacts: snapshot CSVs, ranking JSONs, metadata, and enriched arm CSVs
\item final run summary JSON produced from the redesigned Stage B analysis entry point
\end{itemize}

This package supports both code-level reproducibility and decision-level auditability, which is particularly important once the custom arm is evaluated through authoritative pre-decision binding.
